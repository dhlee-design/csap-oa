# CSAP 정기점검 관리 시스템 기획서 (v0.2)

- 작성일: 2026-11-17
- 대상 서비스: E-GENE 클라우드 ITSM (SaaS 간편등급)
- 상태: v0.2. §9 확정 사항 반영 (2026-11-17)

## 1. 배경과 목적

CSAP 사후평가에서는 지침에 적힌 정기점검을 **주기에 맞춰 실제로 수행했는지**와 **그 증적이 남아 있는지**를 확인한다. 지금은 점검마다 Word/Excel 양식을 따로 관리한다. 그래서 다음 문제가 생긴다.

| 현재 문제 | 사례 (현 산출물 기준) |
|---|---|
| 수행 누락을 알아채기 어렵다 | 백업 점검 결과서의 「백업 준수율」·「복구 테스트」 시트가 비어 있다 |
| 증적 파일이 흩어져 있다 | 체크리스트에는 `접근제어 정책 점검1(261012).png` 같은 파일명만 있고 실제 파일은 별도 폴더에 있다 |
| 월별 이력이 한 파일에 계속 쌓인다 | 접근권한 점검대장은 월마다 시트를 추가한다(202601~202610) |
| 승인 흔적이 약하다 | 점검자/승인자가 이름 텍스트로만 남는다 |

**목표**
1. 점검 일정을 자동으로 만들고 알려서 **누락을 없앤다.**
2. 점검 결과·증적·승인을 **한곳에, 바꿀 수 없는 형태로** 남긴다.
3. 심사 때 **기존 양식(docx/xlsx)과 증적 묶음을 바로 내보낸다.**
4. 새 점검 항목을 **코드 수정 없이 템플릿으로 추가**한다.

## 2. 1차 대상 점검 분석

### 2.1 비정상 통신경로 정기 점검 체크리스트
| 항목 | 내용 |
|---|---|
| 근거 | CSAP 보안인증기준(시스템 격리). ※ 사내 지침에는 이 점검 조항이 없다 (§8 참고) |
| 주기 | 월 1회 |
| 대상 | 서비스 VPC (1건) |
| 역할 | 점검자(이재혁) → 승인자(이동하) |
| 구조 | 4개 구분, 10개 점검 항목, 결과는 Y/N, 비고/증빙 첨부 |
| 종합 | 이상 없음 / 이상 발견 → 이상 내용, 조치 사항, 조치 완료(완료/진행 중) |
| 특이사항 | 이상을 발견하면 **정보시스템관리자에게 즉시 보고** |

점검 항목:
- **서비스 네트워크 외 통신 경로 (3개)**: 보안관제망 경유 여부, 인터넷 직결 우회 경로, 관리망 경유 외부 통신
- **정책 점검(방화벽/접근제어) (3개)**: 미승인 외부 IP, 미승인 포트/프로토콜, 임시·예외 정책 잔존
- **보안관제 로그 점검 (2개)**: 비인가 외부 통신 탐지/차단 이력, 우회 통신 시도 등 이상 징후
- **관리 네트워크 점검 (2개)**: 관리망 외부 통신, 관리 접근 경로의 서비스망 우회

### 2.2 백업 점검 결과서
| 항목 | 내용 |
|---|---|
| 근거 | 서비스연속성관리지침 제11조, 서비스 설계서 11장(백업 대상) |
| 주기 | 월 1회 (+ 복구 테스트는 별도 주기) |
| 역할 | 점검자 → 확인자(정보보호관리자) |
| 기준값 | 보관 180일(지침 ②의 최소 기준은 3개월), 준수율 99% 이상(⑦), 회복 시간 1일(⑧) |

하위 구성:
1. **백업 대상별 점검 (8개 대상)**: 백업 결과(성공/실패/미확인), 최근 백업 일시, 소산 여부, 가장 오래된 백업일, 보관 일수, **보관 기준 충족(자동 계산)**, 이상 내용·조치, 증적 번호
   - 대상: MySQL 전체 DB, 소산 백업, 이용기관별 버킷, 서버 로그, Pod 로그, 서버 이미지, NGS DB(휴네시온), ngs01 로그(휴네시온)
2. **백업 준수율 (월별)**: DB 일 백업과 소산 백업의 예정 횟수(그 달의 일수), 성공 횟수, **준수율과 판정(자동 계산)**
3. **복구 테스트**: 일자, 방식(일부/전체 복구), 결과, 대상 백업 파일, 시작·완료 시각, **소요 시간(자동 계산)**, 확인 내용, 수행자/확인자
4. **증적 목록 (E-01~E-06)**: 증적마다 "무엇을 캡처해야 하는지" 안내가 정해져 있다

### 2.3 접근권한 점검대장 (STEG_CSAP_085)
| 항목 | 내용 |
|---|---|
| 근거 | 접근통제관리지침 제10조 ②, 별지 서식 「접근권한 점검대장」. 작성 후 **정보보호책임자에게 보고** |
| 주기 | 지침에는 "주기적"으로만 되어 있다. 실제 운영은 월 1회 (§8 참고) |
| 구조 | **대상 시스템 14개 × 점검 기준 7개 = 98칸**. 칸마다 점검 결과와 결과 상세(이상 없음/대상 없음/조치 내용 등)를 적는다 |
| 대상 시스템 | SSL VPN, steg-k8s-node-w-8c61/-90b8, new-steg-web01~05, priv-steg-web05, new-steg-bastion, new-steg-ngs01, monitor-steg01, steg-prod-mysql-svc, steg-redis-svc2-001-42n0 |
| 점검 기준 | ① 공식 절차에 따른 권한 부여 ② 업무 목적 및 보안 규정 부합 ③ 승인자 적절성 ④ 직무 변경 시 권한 회수 ⑤ 과도한 권한 ⑥ 유휴 계정 ⑦ 특권 계정 사용 적절성 |
| 관련 대장 | 081 계정·권한 관리대장, 083 서버관리자 계정, 084 특수권한 계정 (점검할 때 대조하는 자료) |

### 2.4 세 점검의 공통 구조
분석해 보니 세 점검 모두 아래 공통 구조로 표현할 수 있다. 이것이 **템플릿 엔진 설계의 근거**다.

```
점검 템플릿 ─ 근거 조항, 주기, 역할(점검자/승인자), 기준값
  └ 섹션(N개)
      ├ 체크리스트형  : 항목 × 결과(Y/N) + 비고 + 증적        ← 2.1
      ├ 매트릭스형    : 대상 × 기준 → 결과 + 상세             ← 2.3
      ├ 표(행 입력)형 : 대상별 행, 열 정의, 계산 열            ← 2.2-1/2/3
      └ 종합/조치     : 이상 여부 → 이상 내용·조치·완료 여부
  └ 증적 슬롯 ─ 증적 번호, 캡처 안내, 필수 여부
```

## 3. 핵심 기능

### 3.1 점검 일정 관리 (누락 방지의 핵심)
- 템플릿의 주기(월/분기/반기/연, 기준일, 마감일)에 따라 **점검 회차를 자동 생성**한다. 예: `2026-11 백업 점검`
- 상태: `예정 → 진행 중 → 승인 요청 → 승인 완료` (+ `반려`, `기한 초과`)
- **알림**: 마감 D-7, D-3, 당일, 기한 초과 시 담당자에게 알리고, 초과되면 승인자에게도 알린다
- **대시보드**: 이번 달 할 일, 기한 초과 건, 점검별 12개월 수행 현황(히트맵). 사후평가 대비 "빈 달" 확인용

### 3.2 점검 수행
- 템플릿 기반 입력 폼. **지난 회차 결과 불러오기**를 지원한다 (접근권한 98칸처럼 대부분 "이상 없음"인 경우 시간이 크게 줄어든다)
- 일괄 입력: 매트릭스에서 "전체 이상 없음" 후 예외만 수정
- 자동 계산: 보관 일수, 기준 충족, 준수율·판정, 복구 소요 시간
- **이상 발견 처리**: 결과가 N이거나 이상이면 이상 내용·조치 입력이 필수가 되고, 지정된 보고 대상자에게 즉시 알린다. 조치가 완료될 때까지 **조치 추적 항목**으로 남는다

### 3.3 증적 관리
- 항목이나 증적 슬롯에 파일을 바로 업로드한다 (캡처 붙여넣기, 드래그 앤 드롭)
- 업로드 시 **SHA-256 해시, 업로더, 시각을 기록**하고, 파일명은 규칙에 따라 자동으로 바꾼다. 예: `E-01_MySQL백업목록_202611.png`
- 필수 증적이 비어 있으면 승인 요청을 막는다
- 증적 슬롯마다 "무엇을 캡처할지" 안내 문구를 표시한다 (백업 「증적 목록」 시트 내용 활용)

### 3.4 승인과 무결성
- 점검자가 제출하면 승인자가 승인하거나 의견을 달아 반려한다
- **승인 후에는 잠긴다**. 수정이 필요하면 "정정 회차"로 새 버전을 만들고 원본을 보존한다
- 모든 변경을 감사 로그에 남긴다 (누가, 언제, 무엇을 바꿨는지)

### 3.5 내보내기 (심사 대응)
- 회차 단위: 기존 양식과 같은 **docx(체크리스트) / xlsx(백업 결과서, 접근권한 대장)**
- 접근권한 대장은 기존처럼 **표지, 개정내역, 월별 시트**를 갖춘 연간 통합 xlsx로 만든다. 개정내역은 회차 이력에서 자동 생성한다
- **기간 일괄 패키지**: 예를 들어 2026-01~10 전 점검을 ZIP으로 묶는다. 폴더 구조는 [별첨3] 증적 제출 폴더 체계(예: `10.1.2 접근기록 관리/`)를 따른다

### 3.6 기준정보 관리
- **대상 자산 마스터**: 서버, 시스템, 백업 대상 목록. 접근권한·백업 점검이 함께 쓴다. 041 자산관리대장 xlsx에서 가져오기를 지원한다
- 사용자와 역할: 점검자, 승인자, 정보보호관리자/책임자, 관리자
- 템플릿 관리: 점검 항목, 주기, 역할, 증적 슬롯을 화면에서 편집한다 (버전 관리, 진행 중인 회차에는 영향 없음)

## 5. 데이터 모델 (개요)

| 엔티티 | 주요 필드 |
|---|---|
| `InspectionTemplate` | 코드, 이름, 근거 조항, 주기 규칙, 마감 규칙, 역할 정의, 버전, 섹션/필드 스키마(JSON) |
| `Asset` | 이름, 유형(서버/DB/VPN/스토리지), 관리 주체, 사용 여부 |
| `InspectionRun` (회차) | 템플릿 버전, 기간(예: 2026-11), 마감일, 상태, 점검자, 승인자, 점검일 |
| `RunResult` | 회차, 섹션·항목·대상 키, 값(JSON), 비고 |
| `Evidence` | 회차, 슬롯/항목, 파일 경로, 원본 파일명, SHA-256, 업로더, 업로드 시각 |
| `Finding` (이상·조치) | 회차, 항목, 이상 내용, 조치 사항, 상태, 완료일 |
| `Approval` | 회차, 단계, 결정(승인/반려), 의견, 처리자, 시각 |
| `AuditLog` | 행위자, 행위, 대상, 변경 전·후, 시각 |
| `User` | 이름, 이메일, 역할 |

템플릿은 섹션과 필드를 JSON 스키마로 정의한다. 그래서 새 점검을 추가할 때 **DB 마이그레이션이나 코드 배포가 필요 없다.**

## 6. 기술 구성 (제안)

| 영역 | 제안 | 이유 |
|---|---|---|
| 앱 | Next.js (App Router) + TypeScript | 화면과 API를 한 저장소에서 관리, 사내 소규모 운영에 적합 |
| DB | SQLite + Prisma (서버 이전 시 PostgreSQL로 전환) | 로컬 PC 우선 운영, 마이그레이션 관리 |
| 파일 저장 | 로컬 디스크 (이전 후 사내 서버 디스크 또는 NCP Object Storage) | 방화벽 정책 캡처 같은 **민감 증적**이 있어 외부 SaaS 저장은 피한다 |
| 인증 | ID/PW + TOTP 2단계 인증 | 접근통제 지침 준수 |
| 알림 | 이메일(SMTP) + 메신저 웹훅 | 일정 알림, 이상 보고 |
| 스케줄러 | 앱 내장 cron (매일 1회 회차 생성·알림) | |
| 내보내기 | docx: `docx` 라이브러리, xlsx: `exceljs` (**기존 양식 파일을 템플릿으로 채워 넣는 방식**) | 심사 제출 양식 유지 |
| 배포 | 1차: 로컬 PC 실행 / 이후: 사내망 또는 NCP 내부 VM (Docker) | 증적 보안. 인터넷 공개 불필요 |

> 로컬 PC 운영 중에는 PC가 꺼져 있으면 알림이 나가지 않는다. 그래서 앱을 켤 때 밀린 회차 생성과 알림을 한 번에 처리(catch-up)하고, 대시보드에서도 기한을 항상 보여 준다. 증적 폴더와 DB 파일은 정기 백업 대상에 넣어야 한다.

> 이 시스템은 **CSAP 증적 자체를 보관**하므로 시스템도 접근통제 지침(접속 기록, 권한 관리)을 지켜야 한다. 시스템 자체가 심사 대상이 될 수 있다.

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| **1단계 (MVP)** | 템플릿 엔진(3종 섹션), 3개 점검 템플릿 등록, 회차 자동 생성, 입력·증적 업로드, 승인·잠금, 대시보드 | 11월 회차를 시스템에서 수행하고 승인까지 완료 |

| **3단계** | docx/xlsx 양식 내보내기, 기간 일괄 ZIP 패키지, 기존 2026년 데이터 이관(접근권한 202601~202610 등) | 2026년 연간 증적 패키지를 한 번에 생성 |

## 8. 지침 검토 결과와 확장 후보

### 8.1 지침과 실제 운영의 차이 (심사 전 정리 권고)
| 점검 | 차이 | 권고 |
|---|---|---|
| 비정상 통신경로 | 체크리스트는 "매달 1회"를 기준으로 하지만, 찾아본 지침(접근통제, 가상화보안, 서비스연속성)에는 근거 조항이 없다 | 접근통제관리지침에 네트워크 격리 점검 조항(주기·서식)을 추가하거나, 근거 지침을 명시 |
| 접근권한 점검 | 지침 제10조 ②는 "주기적으로"만 규정, 실제는 월 1회 | 지침에 "월 1회"를 명시하면 시스템 주기와 일치 |
| 접근권한 점검 | 서식 번호가 본문은 "별지 제5호", 서식 페이지는 "별지 제6호"로 다르다 | 지침 개정 때 번호 통일 |
| 백업 점검 | 지침 ③은 "소산은 6개월마다", ⑤는 "소산 일 백업"으로 표현이 섞여 있다 | 시스템은 ⑤(일 백업)를 기준으로 하되 지침 문구 정리 권고 |
| 백업 점검 | 복구 테스트의 수행 주기가 지침에 없다 | 주기(예: 반기 1회)를 정해 지침에 반영하고 시스템에 등록 |

## 9. 확정 사항 (2026-11-17)
| # | 항목 | 결정 | 설계 반영 |

| 1 | 운영 환경 | **우선 로컬 PC**, 이후 서버 이전 | SQLite + 로컬 디스크 증적 저장으로 시작. 설치 없이 실행 가능한 구성. 서버 이전에 대비해 DB(Prisma)와 파일 저장소를 추상화하고 Docker 설정을 함께 둔다 |
